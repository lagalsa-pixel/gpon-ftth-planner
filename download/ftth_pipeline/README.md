# FTTH-конвейер: от снимка населённого пункта до карты сети и спецификации

Переиспользуемый инструмент, обобщающий методику, отработанную на проекте
«6 СНП Восточно-Казахстанской области» (Верхнеберезовка, Солнечное, Перевальное,
Винное, Пригородное, Алтайский; 2 765 обслуживаемых домохозяйств после полной
VLM-верификации, схемы A/B/C/D, карты зон ОРШ; сметы исключены из комплекта
по решению заказчика — Task 46: «исключи из комплекта сметы — их делать не
нужно»). Конвейер воспроизводит весь путь — от точки заказа на село до карты
с нанесённой сетью и книги материалов — и проверен двумя тестами: **точное
воспроизведение эталонного BoQ ВКО** (все значения сошлись) и **полный
сквозной прогон на новом селе** (Бобровка, 817 ДХ).

Итоговый алгоритм проектирования зафиксирован в **`ALGORITHM_FTTH.md` (v1.1,
Task 48)** — включает сверку с 6 отраслевыми материалами и раздел VII
«Оптический бюджет» (реализован в этом конвейере, v2.4).

## 2. Быстрый старт

```bash
pip install -r requirements.txt

# 1) подготовить config.json: список сёл (name, lat, lon, hh), см. config_example.json
# 2) запустить все стадии:
python3 ftth_pipeline.py --config config.json --stage all

# или по стадиям (каждая идемпотентна, кэши внешних запросов на диске):
python3 ftth_pipeline.py --config config.json --stage fetch        # OSM + снимки
python3 ftth_pipeline.py --config config.json --stage households   # домохозяйства
python3 ftth_pipeline.py --config config.json --stage anchor       # здание ЦУ/ОРШ  <- проверка
python3 ftth_pipeline.py --config config.json --stage network      # топология сети
python3 ftth_pipeline.py --config config.json --stage boq          # материалы A+D
python3 ftth_pipeline.py --config config.json --stage map --vlm    # карта зон + VLM-контроль
python3 ftth_pipeline.py --config config.json --stage xlsx         # спецификация
python3 ftth_pipeline.py --config config.json --stage qa           # проверки
python3 ftth_pipeline.py --config config.json --stage boq --village prigorodnoe  # одно село
```

Результаты: `download/<NN>_<Село>_зоны_ОРШ.jpg` (карта), `download/BoQ_FTTH_<проект>.xlsx`
(спецификация), промежуточные данные — `work/<key>/`.

## 3. Стадии конвейера: что делается и почему

### 3.1. fetch — исходные данные села

**Вход:** координата заказа (центр села), ожидаемое число ДХ.
**Выход:** `work/<key>/osm.json` (дороги/здания/POI), `mosaic.jpg` (мозаика Google z18),
`geo.json` (геопривязка: west/north/mpp/W/H).

1. **OSM** качается через `api.openstreetmap.org/api/0.6/map` чанками ~2,1×2,1 км
   (Overpass API в регионе оказался недоступен; OSM API отдаёт полные данные —
   дороги + контуры зданий). Кэш XML на диске, повторный запуск ничего не качает.
2. **Зондажная область** = радиус `radius_m` + 900 м вокруг точки заказа.
3. **Граница застройки (v3):** только здания (дороги НЕ участвуют в связности —
   они «щупальцами» соединяют разные сёла); сетка 50 м; **морфологическое замыкание
   ~100 м** — мостит пробелы между кустами застройки (критично для линейных сёл
   вдоль реки/дороги); компоненты со ≥15 зданиями; центроид в пределах 65 % зонда;
   при нескольких компонентах — отсечение чужих поселений по имени (Nominatim
   reverse, кэш). Отступ границы +300 м. Ручной override — `bbox_lock` в конфиге.
4. **Мозаика Google Satellite z18** (~0,38 м/px на 50° с.ш.; z19 — апскейл, ESRI z18
   в регионе — заглушки, максимум ESRI — z17). Точная геопривязка: запад/север bbox
   → пиксели, м/px по широте. Тайлы кэшируются в `work/tiles/g18/`.

### 3.2. households — домохозяйства

**Выход:** `work/<key>/households.json` (+ `households_preview.jpg` для контроля).

1. **OSM-здания в зоне села** — основной источник (в ВКО покрывал 95–105 % для
   компактных сёл). Зона: bbox либо фиксированный радиус от точки заказа
   (`zone: {"type":"radius","r":900}` — для сёл, слившихся с соседними).
2. **CV-суплемент** (детекция крыш по снимку: HSV-маски цветов кровли + морфология;
   фильтры площади 40–350 м², компактности, вытянутости) включается автоматически
   при дефиците OSM >15 % (`cv_supplement: auto|on|off`). Строгие контекст-фильтры:
   кандидат ближе 75 м к дороге, не ближе 15 м к OSM-зданию, рядом (<90 м) другие
   объекты. В ВКО это добавило верхнеберезовке/перевальному/алтайскому недостающие дома.
3. **Кластеризация усадеб:** все здания ближе 16 м — одна усадьба (двор).
4. **Фильтры ДХ:** главное здание ≥36 м², центр двора ≤60 м от дороги.
   Результат сопоставим с числом заказа (в ВКО: −15…+12 %; отклонения >
   25 % — сигнал проверить превью/VLM или данные заказа).
5. **Уточнение v3 (с v2.3, `hh_refine: true` по умолчанию)** — критерии
   пользователя (Task 46): различие ЦВЕТА крыш НЕ достаточно (пристройка тоже
   другого цвета, но прямоугольник меньшего размера, отличной формы в плане);
   признаки двух владений — увеличенные размеры, ограждение у ЦЕНТРА фасада
   перпендикулярно ему, общая кровля одинаковой формы (иногда двух цветов):
   - **A. Сплит сблокированных домов — два канала.** Один OSM-полигон может
     покрывать ДВА домовладения, разделённых межевым забором (кейс ВКО:
     бордовая + серая крыши в одном полигоне). Общее: «увеличенные размеры»
     (bbox ≥ 165 м², длинная сторона ≥ 12.5 м), линия раздела только у
     ЦЕНТРА фасада (t = 0.38–0.62, обе оси), части ≥ 36 м².
     - **A1 «двухцветная пара»:** хроматический сплит (dE_ab ≥ 8.5 при
       dE ≥ 18, или нейтральная+окрашенная, или оттенки ≥ 25°) при
       СОПОСТАВИМЫХ частях (ratio ≥ 0.35 — анти-пристройка);
     - **A2 «одноцветная пара»:** геометрический центр-сплит — только при
       найденном ШВЕ/СТЫКЕ кровель (градиент яркости на линии раздела
       покрывает ≥ 45 % среза) — CV-заместитель признака ограждения.
     Солнечный/теневой скат одного дома различаются яркостью L, но не
     хроматикой — и не сплитится.
   - **B. Сплит дворов:** усадьба с 2+ дом-размерными (≥60 м²) зданиями.
   - **C. Многоэтажки** (детерминированно): `building=apartments` или
     `levels ≥ 3` (при sane-проверке площади этажа 40–3500 м²); N квартир =
     min(эт × S/55, эт × подъезды × 4), подъезды ≈ длинная сторона / 28;
     позиции квартир распределяются вдоль фасада.
   - **Верификация A/B — VLM** (`hh_vlm_verify: true`): кроп с контуром и
     двором (pad 35 м), вопрос о числе владений с критериями пользователя
     (увеличенные размеры; забор перпендикулярно фасаду ближе к центру,
     продолжающийся вглубь двора; одинаковая форма кровли; пристройка =
     меньший прямоугольник — НЕ владение). Сплит применяется при
     n ≥ 2 И НЕ пристройка И есть признак раздела. Если VLM недоступен —
     A/B не применяются (консервативно). Агрессивный режим без VLM:
     `hh_split_no_vlm: true`.
   - Валидация (ВКО, Верхнеберезовка, 86 меченых кандидатов): recall
     подтверждённых сплитов 39/40 (98 %); признак «забор между частями»
     разделяет подтверждённые/отклонённые случаи идеально (40/40 vs 0/46).

### 3.3. anchor — здание-якорь ЦУ/ОРШ [точка ручной проверки]

**Выход:** `anchor_candidates.json` (топ-5) + `anchor_preview.png` (кроп с обводками).

Скоринг: `размер (150–500 м²) × центричность (к центроиду ДХ) × близость к главной
дороге × компактность × бонус общественного здания`. Топ-1 — кандидат по умолчанию;
если он не подходит (в Бобровке это оказался храм 22 м²) — задать
`force_anchor: <osm_id>` из списка кандидатов. В ВКО по кропам дополнительно
проверяли VLM (здание у перекрёстка, не сарай и т.п.).

### 3.4. network — древовидная сеть

**Выход:** `work/<key>/network.json` (ОРШ, муфты, дропы, магистраль, статистика).

1. **Дорожный граф OSM:** денсификация до 4 м, сварка общих узлов.
2. **Привязка:** ОРШ и каждое ДХ снаппятся к ближайшему узлу графа (допуск 90 м;
   медиана в ВКО — 17–21 м).
3. **MST терминалов по метрике кратчайших путей по дорогам** (Дейкстра от всех
   терминалов) → объединение путей → **SPT-дерево от ОРШ** (кратчайшие пути от корня
   по объединённому подграфу). Сеть всегда следует улицам, а не «по прямой».
4. **Муфты:** (а) слияние точек подключения в радиусе 50 м по пути к ОРШ;
   (б) ВСЕ узлы ветвления дерева (степень ≥3); (в) дедупликация муфт ближе 15 м
   по дереву; (г) промежуточные муфты через ~100 м при дропе >120 м.
5. **Дропы:** от обслуживающей муфты вдоль улицы + ломаная по двору/фасаду
   (не по прямой — вдоль заборов/участков, изломы детерминированы хэшем id ДХ).
6. **Магистраль** = объединение путей муфта→ОРШ.

Типовые результаты (ВКО): 1,8–2,4 ДХ/муфту, ср. дроп 32–45 м, макс 73–133 м.

### 3.5. crop — пользовательский кадр (опция)

Если заказчик даёт свой обрезанный снимок (`crop_image` в конфиге):
1. **SIFT+FLANN+RANSAC** (даунскейл ×4, CLAHE): частичная аффина кадр↔мозаика;
   контроль NCC. В ВКО все кадры привязались с 97–99 % inliers, масштаб 0,5
   (двукратный апскейл заказчика), поворот ~0°.
2. Сеть перестраивается в границах кадра (ДХ только в кадре, клип дорожного графа,
   перевыбор ОРШ при необходимости) → `network_v2.json`.
3. Стадия `map` автоматически рендерит на кадре пользователя (трансформация
   M_inv, размеры маркеров ×1/scale).

### 3.6. boq — материалы: схемы A и D

**Выход:** `work/<key>/boq.json` + сводный `work/boq_total.json`.

**Схема A (централизованная):** сплиттеры 1:64 в ОРШ, выделенное волокно каждому ДХ.
Волокна участка = ceil(1,25 × ДХ потока), минимум 8; разложение на параллельные
кабели 8/12/16/24/32/48/64/72/96 волокон.

**Схема D (зонные ОРШ, рекомендуемая):** дерево села режется на зоны; в корень зоны
(существующая муфта ветвления) ставится зонный ОРШ со сплиттерами 1:64 своей зоны;
единый узел OLT; фидер ЦУ→зонный ОРШ = ceil(1,25 × сплиттеры зоны) — прокладывается
по КРАТЧАЙШЕМУ пути дорожного графа (Дейкстра; v2.1). На участках, общих с деревом
распределения, фидерные волокна едут в одном кабеле с распределительными; на
участках вне дерева — отдельный кабель ≥ min_fibers (8 волокон). **Жадное разбиение**:
врезы выбираются по максимальной маржинальной экономии волокно-км (точный пересчёт
полной раскладки на каждом шаге); зона ≥48 ДХ (заполнение сплиттера ≥75 %); экономия
вреза ≥ S_MIN (15 волокно-км — порог окупаемости шкафа).

> **Почему именно кратчайший путь (v2.1).** Дерево распределения — приближение
> дерева Штейнера: оно минимизирует СУММАРНУЮ длину сети, но маршрут
> «точка-точка» внутри него может быть вдвое длиннее кратчайшего по улицам
> (проект ВКО, с. Пригородное, ОРШ-2: 1313,6 м по дереву против 683,9 м по
> кратчайшему пути — маршрут, проверенный в Google Earth). Дополнительно
> фидерные волокна внутри распределительного кабеля вскрываются в каждой муфте
> на пути (~21 тыс. сквозных сварок на проект ВКО не учитывались бы вовсе), а
> отдельный кабель проходит муфты без сварок — сварки только на концах (уже
> в формуле). Цена: +4,8 % закупочного кабель-км (участки 8F вне дерева) при
> −0,9 % волокно-км и −12 % длины фидерных трасс. В ВКО схема D с v2.1 даёт
> 180,1 км суммарного кабеля (A: 202,3 км) при волокно-км −64 %; состав зон
> при повторной оптимизации не меняется.

**Встроенные инварианты:** без врезов D точно воспроизводит A (волокно-км, сплиттеры);
ДХ/дропы/трасса A=D; сумма домов зон = ДХ села. Нормы расходников: сварки
(2×ДХ + 2×сплиттеры)×1,1; подвесы 30/км; анкеры 2/ДХ; крепёж 6/ДХ; порты ОРШ
ДХ×1,1 → ряды 144–1152 (ЦУ) / 48–576 (зонные); запасы: магистраль +10 %, дроп +5 %.

**Оптический бюджет (v2.4, §VII ALGORITHM_FTTH.md v1.1):** для худшего
абонента каждой зоны считается затухание линии
`A = 0,35×L + 21,0 (PLC 1:64) + 3×0,5 (SC/APC) + (4+n_транз)×0,1 + 0,2` дБ,
где L = фидер ЦУ→ОРШ + худший путь дерева ОРШ→муфта + макс. дроп.
Гейты: A + 3 дБ ≤ 28 дБ (Class B+) — «ok»; A ≤ 28 — «ok-hard» (зоне
указывается оптика Class C+ или сплиттер 1:32); A > 28 — «EXCEEDED»
(редизайн зоны). Результат — в `boq.json` → `optical_budget`, проверка —
в стадии `qa` (гейт `budget`). На эталоне ВКО: все зоны в B+, худшая
линия 27,42 дБ (маржа 0,58 дБ).

### 3.7. map — карта зон ОРШ

**Выход:** `download/<NN>_<Село>_зоны_ОРШ.jpg` (JPG q90 4:4:4) + превью
`work/qa/zone_maps/<NN>_preview.png`.

Слои (снизу вверх): оболочки зон (выпуклые оболочки, α38) → дропы (жёлтые) →
ствол (серый) → распределительная сеть зоны (цвет зоны) → фидер ЦУ→ОРШ (пунктир
цвета зоны с фазовым сдвигом — «косичка» на общих участках) → муфты → ДХ (цвет
зоны) → зонные ОРШ (шкаф с подписью «ОРШ-N / N ДХ») → ЦУ (красная звезда).
Шапка со статистикой, легенда зон с параметрами каждой зоны, условные обозначения,
масштабная линейка, стрелка севера. **Легенда размещается автоматически** из 5
позиций (BL/BR/ML/MR/TL) по минимуму взвешенного перекрытия (ДХ=1, муфта=2,
ОРШ=20, ЦУ=50). Подписи — жадное размещение без наложений.

> Превью 1800 px — для контроля зон/легенды/подписей; масштабная линейка и стрелка
> севера тонкие и на глубоком даунскейле могут не читаться — на полноразмерной
> карте они есть (проверено пиксельно).

### 3.8. xlsx — спецификация материалов

**Выход:** `download/BoQ_FTTH_<проект>.xlsx` — 4 листа:
«Сводная (схема D)» (4 секции А–Г, живые формулы SUM по селам и ИТОГО),
«Параметры сетей» (17 граф + итоговая строка), «Схемы A и D» (сравнение 10
показателей с Δ%), «Методика» (auto-генерация с фактическими числами проекта).
Дизайн: Calibri, палитра professional, закрепление панелей, печать в ширину листа.
QA-совместимо: recalc 0 ошибок, validate passed.

### 3.9. qa — контрольные проверки

`--stage qa`: наличие артефактов, отклонение ДХ от заказа, покрытие сети
(обслужено/определено), сумма домов зон = ДХ, размеры карты, **оптический
бюджет без превышений Class B+** (зоны с запасом < 3 дБ помечаются
рекомендацией C+/1:32). Пороговые значения подсвечиваются
«СВЕРИТЬ вручную/VLM».

## 4. Точки контроля человеком (осознанные решения, не баги)

| Точка | Что проверять | Инструмент |
|---|---|---|
| после `fetch` | граница села (не обрезала ли край, не включила ли соседей) | превью мозаики; `bbox_lock` при необходимости |
| после `households` | детекция vs заказ (превью с маркерами) | `households_preview.jpg`; порог ±25 % |
| после `anchor` | кандидат №1 — подходящее здание | `anchor_preview.png`; `force_anchor` |
| после `map` | зоны/легенда/подписи | превью; `--vlm` (если доступен z-ai) |
| линейное село у города | авто-граница может включить город | `zone: {"type":"radius","r":...}` |

## 5. Ограничения и известные особенности

- **Память:** мозаики ~150 Мп (линейное село 6×4 км) требуют ~2–3 ГБ ОЗУ на рендер;
  при нехватке — уменьшить `boundary_keep_frac`/радиус или рендерить по одному селу.
- **Кадр пользователя** должен быть неповернут (|rot| < 0,5°) и иметь общие черты
  с мозаикой для SIFT (в ВКО — все кадры привязались автоматически).
- **Межселённый транспорт** до ЦУ и активное оборудование — за рамками BoQ
  (как и в проекте ВКО).
- **VLM-проверки** опциональны (`--vlm`): требуют CLI `z-ai`; без него конвейер
  полностью детерминирован на геометрических проверках.
- Волокно-км схемы A считается «справочно»: физика выделенного волокна каждому ДХ
  даёт большие ёмкости у ОРШ (в ВКО — до 972 волокон параллельно); схема D снимает
  это ограничение (максимум 128F, ≤2 параллельных кабелей).
